# The token system

Every LST tag is a Java class. There is no table mapping tag names to behaviour — the
classes *are* the mapping, and they declare their own name.

That is why this handbook's [tag index](../lst/reference/tag-index.md) is generated by
reading them.

## The contract

The base interface is small:

```java
public interface CDOMToken<T> extends LstToken
{
    ParseResult parseToken(LoadContext context, T obj, String value);
    Class<T> getTokenClass();
}
```

*Source: [`CDOMToken.java`](https://github.com/PCGen/pcgen/blob/d4ade6d509f4206b1c1789848752e633ec3c134c/code/src/java/pcgen/rules/persistence/token/CDOMToken.java)*

Three things come from that:

| Method | Gives |
|---|---|
| `getTokenName()` | the literal tag string, from `LstToken` |
| `getTokenClass()` | the object type that accepts the tag |
| `parseToken` | what the tag does with its value |

`getTokenName()` and `getTokenClass()` together are the authoritative statement of
which tags are legal in which files.

## Writing back out

Parsing is only half. A token also regenerates its own text:

```java
public interface CDOMWriteToken<T> extends LstToken
{
    String[] unparse(LoadContext context, T obj);
}
```

Most tags implement both halves through `CDOMPrimaryToken`, which combines them and
adds nothing of its own:

```java
public interface CDOMPrimaryToken<T> extends CDOMToken<T>, CDOMWriteToken<T>
```

That is the interface a normal per-tag class implements.

### Why round-tripping matters

`unparse` exists so PCGen can write data back out, but its more useful effect is on
testing. A token's unit test parses a string, then unparses it, and asserts the result
matches.

That makes the tests a reliable statement of what syntax a tag accepts — often more
precise than the documentation. When this handbook needed to know exactly what a tag
takes, the test was the place to look.

## Two-level tags

`ADD:ABILITY` and `CHOOSE:SKILL` are two tokens, not one. The parent claims the tag
name, the child claims what follows the colon:

```java
public interface CDOMSubToken<T> extends CDOMToken<T>
{
    public String getParentToken();
}
```

`CDOMSecondaryToken` extends that and adds the write half.

The full tag is `getParentToken() + ":" + getTokenName()`. There is no shared method
that returns it — each class composes it where needed, and the scanner in this
repository does the same.

## Tokens never touch objects directly

`parseToken` receives the object, but writing to it is not the point of the call.
Tokens write through `LoadContext` into an `ObjectContext`, keyed by an `ObjectKey`
for single values or a `ListKey` for collections.

```java
context.getObjectContext().put(skill, ObjectKey.KEY_STAT, ref);
context.getObjectContext().addToList(cdo, ListKey.TYPE, type);
```

Two reasons this matters:

- **`unparse` reads the changes back** through the same context, which is what makes
  round-tripping possible.
- **Loading is undoable.** Changes are held in the context rather than applied
  directly, so a failed load does not leave half-modified objects.

A token that writes to the object directly breaks both. The `CAMPAIGN:` token does
exactly that, with an in-source note admitting it.

## Return values

`parseToken` returns a `ParseResult`. Success is a shared constant, failure carries a
message:

```java
return ParseResult.SUCCESS;
return new ParseResult.Fail("...");
```

The message is what the reader sees in the log, so it is worth writing well.

## Dispatch

`TokenSupport` resolves a `(object class, tag name)` pair to a token and calls it.
Lookup walks the target object's **class hierarchy**, which is the mechanism behind a
rule this handbook states repeatedly:

- A token declaring `getTokenClass()` as `CDOMObject` works on nearly everything,
  because most things extend it.
- A token declaring `Skill` works only on skills.

So "which tags are legal here" is answered by Java's type hierarchy, not by a list.

*Source: [`TokenSupport.java`](https://github.com/PCGen/pcgen/blob/d4ade6d509f4206b1c1789848752e633ec3c134c/code/src/java/pcgen/rules/persistence/TokenSupport.java)*

## Work that happens after loading

Some tags cannot finish during parsing, because they depend on things not loaded yet.
Three interfaces handle that, running in order after the files are read:

```java
public interface DeferredToken<T extends Loadable>
{
    public boolean process(LoadContext context, T obj);
    public Class<T> getDeferredTokenClass();
}
```

| Interface | Runs |
|---|---|
| `DeferredToken` | after loading, before reference resolution |
| `PostValidationToken` | after reference resolution, for checks across the finished data set |
| `PostDeferredToken` | last |

Both of those declare `getPriority()`, and each set runs in that order among itself.

`BONUS` implements both `CDOMPrimaryToken` and `DeferredToken` — it parses at the line
and validates once everything exists.

*Source: [`DeferredToken.java`](https://github.com/PCGen/pcgen/blob/d4ade6d509f4206b1c1789848752e633ec3c134c/code/src/java/pcgen/rules/persistence/token/DeferredToken.java)*

## Old syntax

`CompatibilityToken` carries a version triple, and `TokenFamily` groups tokens by it.
When the current family has no match for a tag, dispatch falls back to an older family.

That is how data written for an earlier PCGen keeps loading. It is also how a tag gets deprecated without
breaking anything. The old class stays, moves to the `deprecated` package, and logs a
message pointing at the replacement.

## Helper base classes

The token package holds 37 files, and most are shared bases rather than interfaces:

| Base | For |
|---|---|
| `AbstractNonEmptyToken` | rejects an empty value before your code runs |
| `AbstractTokenWithSeparator` | validates a separator such as `\|` |
| `AbstractIntToken`, `AbstractStringToken`, `AbstractYesNoToken` | single typed values |
| `AbstractBasicCampaignToken` | PCC file-reference tags |
| `AbstractSimpleChooseToken`, `AbstractQualifiedChooseToken` | `CHOOSE:` variants |

Picking the right base is most of writing a token. See [adding a tag](adding-a-tag.md).
